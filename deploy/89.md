# 89 生产部署（本 fork）

目标机：`sub2api-89`（与 sub2api 同机）。源码仓：`https://github.com/wuxiran/codex-proxy-rs`。
安装目录：`/opt/codex-proxy-rs`。数据面只给本机 sub2api 用，不把管理端和 PostgreSQL/Redis 暴露到公网。

## 拓扑与端口

```
sub2api ──http://cpr-green:8080──▶ cpr-gate（nginx，持有别名 cpr-green，发版不重启）
宿主机 nginx ─127.0.0.1:18083────▶      │
                                        ├─▶ codex-proxy-rs-green-codex-proxy-rs-1
                                        └─▶ codex-proxy-rs-blue-codex-proxy-rs-1
```

| 服务 | 宿主机 | 说明 |
| --- | --- | --- |
| cpr-gate | `127.0.0.1:18083` | 管理面入口；`cpr.nocannobb.com` 的宿主机 nginx 反代到这里 |
| CPR 槽位 green / blue | 不映射 | 不带网络别名，只被 cpr-gate 按容器名访问 |
| PostgreSQL / Redis | 不映射 | 仅 compose 内部网络 |
| 官方默认 `8080` | **禁止占用** | 已是 sub2api |

sub2api 账号 `my-cpr-codex` 的上游是 `http://cpr-green:8080/v1`（网络 `cpr-sub2-internal`）。
号池、OAuth、出口代理只放 CPR。sub2api 只保存一把 Client Key。

## 发版

**一律走 `deploy/rollout.py`，禁止对槽位容器原地 `compose up` / recreate / restart。**

原因（2026-09-19 事故）：原地重建有几秒端口空窗，sub2api 碰到一次 `connection refused`
就会把账号摘除 10 分钟（上游为「代理失效的坏号」设计的保护），而对应分组只有这一个账号，
结果现网 503 十分钟。`rollout.py` 让新槽位先起、`cpr-gate` reload 切流、旧槽位排空后停，
调用方全程看不到拒连；在途长流留在 nginx 老 worker 和旧槽位上跑完。

```bash
# 构建机：在打镜像的那份检出里生成迁移清单，连同镜像包、metadata.json 传到 89
python3 deploy/rollout.py migrations-manifest backend/migrations > migrations.json

# 89
python3 /opt/codex-proxy-rs/deploy/rollout.py status
python3 /opt/codex-proxy-rs/deploy/rollout.py deploy --metadata <metadata.json> --migrations <migrations.json>
python3 /opt/codex-proxy-rs/deploy/rollout.py rollback      # 旧槽位容器保留为 stopped，拉起后切回
```

- `host.drain_timeout_seconds` 在 89 的 `config.yaml` 里是 `600`（槽位 `stop_grace_period: 11m`）：
  旧槽位排空时新槽位已在服务，所以可以让长回合跑完。**原地重建的部署不要照抄这个值**，
  那里排空期间端口是关着的，排空多久就断多久。
- **含数据库迁移的版本** `deploy` 会直接拒绝（旧槽位要在新 schema 上继续跑到排空结束）。
  这类版本走低峰维护窗口，发完立即在 sub2api 后台清掉账号的临时不可调度状态。
- 逐个确认新增迁移**只增不改**（加列带默认值、加表、放宽约束，旧版本读写不受影响）后，可以
  仍走先起后停：先 `pg_dump -Fc` 全库备份，再
  `rollout.py deploy ... --allow-additive-migrations --db-backup <dump>`。库里已应用的迁移必须
  原样是新清单的前缀，备份须在 2 小时内。**迁移后旧镜像无法再启动**（sqlx 拒绝库里有它不认识的
  迁移），此时 `rollback` 不可用，回退只能用这份备份恢复数据库再用旧镜像发版。
- 有备份任务在 `dumping` / `uploading` 时 `deploy` 会拒绝：备份 worker 按单副本设计，
  新实例启动会无锁「恢复」进行中的备份。
- 只改 `deploy/gate/nginx.conf` 时：`docker exec cpr-gate nginx -t && docker exec cpr-gate nginx -s reload`。
  不要 recreate `cpr-gate`，它一重启就是全量拒连。

## 首次启动（全新机器）

在 `/opt/codex-proxy-rs`：

```bash
docker compose -f deploy/compose.yaml -f deploy/compose.89.yaml config --quiet
docker compose -f deploy/compose.yaml -f deploy/compose.89.yaml up -d --no-build --wait
curl -i http://127.0.0.1:18080/healthz
```

健康检查成功返回 `204`。国内请用：`https://hub.nocannobb.com:8443`（SNI 复用已能打开的 hub，Cloudflare 8443 反代本机 `127.0.0.1:18080`）。
`https://cpr.nocannobb.com` 在部分网络下 TLS 握手会被中间设备掐断，海外或未干扰链路才可用。
管理端也可以走 SSH 隧道 `ssh -J vps-xui -L 18080:127.0.0.1:18080 sub2api-89`。

```bash
ssh -J vps-xui -L 18080:127.0.0.1:18080 sub2api-89
```

浏览器打开 `http://127.0.0.1:18080`，用户 `admin@cpr.local`。

## 镜像

89 内存约 8GiB，不要在生产机编译 Rust。在能构建 `linux/amd64` 的机器上：

```bash
CPR_IMAGE=codex-proxy-rs:89-fork \
CPR_GIT_SHA="$(git rev-parse HEAD)" \
CPR_BUILD_TIME="$(date -u +%Y-%m-%dT%H:%M:%SZ)" \
docker compose -f deploy/compose.yaml -f deploy/compose.89.yaml build codex-proxy-rs
```

把 `codex-proxy-rs:89-fork` 传到 89 后 `docker load`，再执行上面的 `up --no-build`。

在线更新保持关闭，避免容器把二进制换成上游正式包。发我们自己的 Release 之前，不要打开 `CPR_ENABLE_SELF_RESTART`。

## 配置

`deploy/config.yaml` 由 `config.example.yaml` 复制，Git 忽略。PostgreSQL / Redis 密码各 `openssl rand -hex 24`；`admin.default_password` 至少 12 位且不含 `$`。已有数据目录后不要用模板覆盖该文件。

PostgreSQL 18 容器以 uid `999` 写数据目录。首次启动前需要：

```bash
chown -R 999:999 /opt/codex-proxy-rs/.runtime/postgres
chmod 0750 /opt/codex-proxy-rs/.runtime/postgres
```

应用数据和日志仍是 `10001:10001`。不要把 `.runtime/postgres` 也改成 `cpr` 用户，否则会出现 `mkdir: cannot create directory '/var/lib/postgresql'`。

## 观澜 CDK 导入

管理端「导入账号 → OpenAI → 观澜 CDK」由**浏览器**按观澜 SDK 兑换：

1. `POST /guanlan/api/cdk/redeem`
2. `GET /guanlan/api/cdk/redemptions/{id}/download`（`X-Cdk-Download-Token`）
3. 把返回的已签名 JSON 交给现有导入任务

`/guanlan/` 由 Nginx 反代 `https://zzledu.kdns.fr/`，不转发 CPR Cookie。本地 `pnpm --dir frontend dev` 同样走 Vite 代理 `/guanlan`。

CDK 身份 `x-cdk-client` 存在浏览器 localStorage，和观澜网页版一样按浏览器恢复。前端兑换失败（网络/反代）时，才会把 `{ cdks: [...] }` 交给后端再兑一次。

## 401 复活

第三方接口：`https://zzledu.kdns.fr/revive-api`。只接受**已签名**的 Sub2API / CPA JSON，CPR 管理端导出不能直接上传。
脚本在仓库 `tools/revive/revive.py`，89 上可直接用系统 Python 3。

```bash
# 检测签名文件；有 401 则创建复活任务并写出恢复 JSON
python3 /opt/codex-proxy-rs/tools/revive/revive.py recover /path/to/signed.json --out /tmp/revived.json

# 把恢复结果导入本机 CPR（需要管理端 API Key）
CPR_ADMIN_URL=http://127.0.0.1:18080 \
CPR_ADMIN_API_KEY='...' \
python3 /opt/codex-proxy-rs/tools/revive/revive.py import-cpr /tmp/revived.json
```

签名文件含 OAuth 明文，请求会离开 89。不要把 `X-Revive-Task-Token` 或恢复 JSON 写进仓库、工单和普通日志。

## 401 自动复活（内置）

CPR 自己会用 refresh token 续 AT。只有 **RT 被 OpenAI 拒绝、账号进入 Expired** 时，才会走 revive-api 重新拿号。

条件：

1. 号池是**已签名**的 Sub2API/CPA JSON 导入的（导入时会归档到 `.runtime/data/revive/`）。
2. `deploy/config.yaml` 打开开关（默认关）：

```yaml
openai:
  auth:
    revive:
      enabled: true
      base_url: 'https://zzledu.kdns.fr/api/revive/v1'
```

改配置后重建应用容器。Worker 每 60 秒扫描 Expired 的 OAuth 账号，按归档原文提交检测/复活，并把新的 AT/RT 写回**原账号**，不新建重复号。未签名导入、封禁号、以及仍能 RT 刷新的号都不会提交。失败冷却 30 分钟。

## 账号成本、到期与票据恢复

账号行菜单「成本与票据」可记录买入价（CNY/USD）、买入时间、到期时间（例如车主踢人时间）和登录票据
（`邮箱----密码----2FA密钥`）。数据在 fork 子表 `account_tickets`（迁移 9003）；票据以 AES-256-GCM
加密后入库，密钥在 `.runtime/data/account_tickets/ticket.key`（两个槽位共享，**不要删**，删了已存票据
全部无法解密，只能重新录入）。

「用票据恢复」由 CPR 调用同机 sidecar `cpr-ticket-login` 走账号绑定的出口重新登录，核对新令牌属于同一
用户与工作区后写回原账号：

```bash
# 构建机（在 chatgpt-register 目录，用干净的上下文只带 4 个源码文件）
docker build -f Dockerfile.ticket-login -t cpr-ticket-login:<tag> <ctx>
# 89
docker load -i cpr-ticket-login-<tag>.tar.gz
CPR_TICKET_LOGIN_IMAGE=cpr-ticket-login:<tag> docker compose -f deploy/compose.ticket-login.yaml up -d
```

`config.yaml`：

```yaml
openai:
  auth:
    ticket_login:
      enabled: true
      base_url: 'http://cpr-ticket-login:8080'
      token: '<与 .runtime/ticket-login.env 相同>'
```
